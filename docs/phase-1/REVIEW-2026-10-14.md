- **Historical difference:** preserved alternatives, not a new defect.

Source citations give repository paths and original line ranges at review time.
The snapshot inventory alongside this report identifies all reviewed bytes.
No claim below establishes a simulator, RTL, or physical-board failure.

### F3 resolution — approved

The new Phase 1 handoff uses the Master's single `SWITCH CR15`: save the
outgoing Thread under the outgoing Namespace, load the destination Namespace,
then activate its slot-2 entry Thread using the specified permissionless Inform
GT with version 0. There is no following CHANGE and no programmer-visible
instruction boundary between these phases.

Supersede the first-pass draft's SWITCH-then-CHANGE recipe and its shared
transition-context requirement insofar as that requirement exists only to bridge
the two-instruction interval. Preserve ordinary admission and validation checks.
One instruction does not promise rollback of outgoing-save writes: failures
remain hard faults under the Master's contract. Apply the approved F5 CR13 rule.

**Decision:** The user selected the single combined SWITCH CR15 handoff and
clarified: “Switch is a special case of CHANGE but Change without CR15 remains.”
The user's subsequent explicit clarification defines the relationship:

```text
CHANGE: THREADSAVE → THREADLOAD
SWITCH: THREADSAVE → LOAD NAMESPACE (CR15) → THREADLOAD
```

CHANGE consists of the two halves THREADSAVE and THREADLOAD. SWITCH is a
version of CHANGE that inserts the Namespace load between those same halves:
THREADSAVE uses the outgoing Namespace; THREADLOAD uses the incoming Namespace.
Ordinary CHANGE leaves CR15 unchanged. CR13 remains NULL and is never touched.
These phase names describe the instruction's internal sequence, not separate
programmer-issued instructions.

The assistant's qualification about preserving other SWITCH forms is withdrawn
from this resolution; it was not part of the user's approval. Conflicting
protected-load descriptions must be reconciled against this clarified definition,
not treated as independently reaffirmed behavior.

This is document reconciliation, not a claim that the simulator, RTL or
installed images already implement the combined handoff.

### F4 resolution — approved

Require a bounded execution turn: a Thread cannot avoid its deadline merely by
continuing to retire instructions. Retirement and ordinary CALL/RETURN do not
renew the budget. Expiry produces a watchdog hard fault, not automatic IRQ
preemption or an implicit successful handoff.

**Decision:** The user selected bounded execution turns and specified:
“The WATCHDOG TIME VALUE is defined as ONE second to Hard Fault unless in
IDE debug or IDE Trace mode.”

The watchdog deadline is **one second**, with an exception while in **IDE Debug
or IDE Trace mode**. Continued instruction retirement does not prevent expiry.
No IRQ delivery, CR13 use or automatic successful handoff is introduced.
Do not replace this fixed duration with an arbitrary target-dependent timeout.

**Renewal decision:** The user selected **every successful CHANGE or SWITCH**.
Each completed transfer starts a fresh one-second interval, including
self-transfers and transfers between helper Threads. No scheduler identity or
special scheduler authorization is required for watchdog renewal.
Failed or condition-skipped transfers are not successful transfers and do not
renew it. Ordinary instruction retirement and CALL/RETURN do not renew it.

The bound is therefore on time between successful transfers, not a guarantee
that execution returns to a scheduler or makes useful application progress.
Repeated successful transfers may renew indefinitely; this is an explicit
consequence of the selected rule, not an unapproved scheduler-only restriction.

**Mode-exit decision:** The user selected a fresh second. When neither IDE Debug
nor IDE Trace is active and normal execution resumes, start a new one-second
interval rather than resuming a previously remaining duration. Switching between
the two exempt modes does not end the exemption while either remains active.

**Startup and deadline rules — approved by the user:**

- Arm a fresh interval when execution starts after reset, including boot, unless
  IDE Debug or IDE Trace is active.
- Measure one second of elapsed time using the target's timing source, not an
  instruction count; executing slowly or stalling does not extend the interval.
- At the one-second boundary expiry wins. CHANGE/SWITCH must complete strictly
  before the deadline to renew it; beginning a transfer is insufficient.

**F4 outcome:** The user approved these remaining rules, completing the
architectural timing policy. No additional maintenance exception or new
timer/control-register ABI is approved. Source-document reconciliation and
simulator/RTL/board conformance evidence remain separate work, not implied by
this documentation resolution.

### F6 resolution — width and software/hardware boundary approved

Use a 9-bit gt_seq, values 0–511, consistently in the GT and corresponding
Namespace descriptor. Mark 7-bit/0–127 descriptions as legacy and correct
active work-plan requirements. Selecting the width does not approve modulo-512
reuse: any exhaustion/wrap policy belongs to software, not hardware.

**Width decision:** The user selected 9 bits, values 0–511. The width is approved;
wrapping or reusing generations is not.

**User clarification:** “The generation counter is software controlled and
hardware is not involved beyond checking for equality.”

Software exclusively manages the generation value. Hardware compares the
GT generation with the corresponding Namespace descriptor generation and faults
on mismatch. It does not increment, enforce exhaustion, detect or regulate
wraparound, or maintain a wrap-rate timer. This boundary concerns generation
management; it does not remove the other ordinary capability checks.

The previous no-wrap proposal was not approved and is not a Phase 1 requirement.
Remove the security work plan's hardware wraparound-guard requirement when
reconciling the documents. Do not introduce a replacement hardware policy.

A time delay between wraps alone cannot prove that old capabilities no longer
exist. The work plan's proposed one-second wrap guard therefore cannot establish
safe reuse and must not be confused with the approved execution watchdog.

**Scope:** Width and hardware responsibility are resolved. Software's exact
reuse/exhaustion policy remains unspecified, rather than implicitly approved as
modulo wrap, no-wrap rejection, or safe reuse. Equality checking alone does not
prove that an old capability cannot match a reused generation.

## Detailed findings

### Phase 1 capacity decision — approved

The user raised increasing the starting Namespace capacity from 64 to 256 slots
instead of making the IDE's object catalog conform to a small hardware table.
The user approved **256 total slots as the Phase 1 starting/default
capacity**, retaining configurable geometry rather than a new ISA maximum.

At four 32-bit words per slot:

| Capacity | Table words | Table bytes | CR15 word-offset limit |
|---|---|---|---|
| 64 | 256 | 1,024 | 255 |
| 256 | 1,024 | 4,096 | 1,023 |

The increase is 768 words / 3,072 bytes. N includes metadata slot 0. Existing
slot identities, including the approved slots 0–2, 8, 9, 14 and 15, need not be
renumbered. Resident-body locations must be recalculated for overlap, alignment
and total allocation; do not blindly add an offset to every word or token.

This approval establishes the target capacity, not certification of the existing
bitstream. The new-image header/count encoding, allocation size, CR15 bounds,
relocated descriptors and integrity values, image generation, simulator/RTL
behavior, ROM/address assumptions and exact bitstream acceptance must agree.
Published slot-id width supports indices through 255, but that alone does not
prove the whole build supports this table size.

This expansion does not itself solve backing-memory capacity or define
virtualGT encoding. Any ID-range convention based on slot count must use the
selected capacity; existing virtual IDs cannot silently become physical
bindings because the table grew.

**Decision:** The user selected “Approve 256 slots.” Slots are numbered 0–255,
including metadata slot 0. Existing approved slot assignments remain unchanged.
Capacity remains configurable, not hardwired as a new architectural maximum.
No saved-image migration, rebuild, upload or FPGA programming is authorized or
performed by this documentation decision.

### F1 — Namespace layout and fixed slots do not describe one image

**Conflict between current ISA and unqualified supporting layout/configuration text.**

- `docs/instruction-set.md:375–407`: an ascending table begins at the allocation
  base; slot 0 is four-word metadata, slot 1 is the Namespace self-entry, slot 2
  is the designated entry Thread; CR15 covers the table with limit `4*N - 1`.
- `docs/boot-rom-layout.md:25–58`: LOAD from slot 0, Boot.Thread in slot 1,
  a separate **16-word Header V2**, and a **tail-anchored** table.
- `docs/namespace-plan-contract.md:39–44`: UART_DEV must occupy **NS[2]**.
- `docs/CM_LUMP_SPECIFICATION.md:1804–1820`: slot 0 is the Namespace's own
  descriptor rather than the physical metadata specified by the current master.
- `docs/architecture.md:30–40, 523–535` distinguishes existing target profiles;
  this is useful implementation context, but does not select a conforming new
  Phase 1 image or settle migration.

**Why it matters:** applying these documents together places different objects
in slot 2 and produces incompatible offsets and bounds.

**Required resolution:** label the legacy/profile-specific documents explicitly,
then freeze one Phase 1 geometry and slot map. Preserve old images as evidence.
Do not move UART or regenerate images merely to make the prose agree.

### F3 — The handoff draft still instructs an extra CHANGE

### F4 — “Watchdog progress” and “bounded yielding” are different guarantees

**Conflicting design goals/refresh rules; not a proved implementation defect.**

- `docs/architecture.md:328–350` says run-to-suspension must not allow an
  unbounded loop, but resets the watchdog counter whenever an instruction
  retires **or** a suspension/handoff occurs.
- The cooperative scheduling review,
  `reports/isa-review-cooperative-round-robin-hard-faults.html:525–543`,
  gives workers an elapsed-time budget and says ordinary CALL/RETURN do not
  yield or renew it.
- `docs/instruction-set.md:127–135` still leaves watchdog/platform decisions open.

A loop that keeps retiring instructions can satisfy a retirement watchdog
indefinitely while never yielding. Detecting a stalled core and enforcing a
Thread's handoff deadline are not interchangeable.

**Required resolution:** select the Phase 1 guarantee and define its reset event,
timebase, enable/pause rules and expiry action. If both guarantees are needed,
specify them separately rather than claiming one timer proves both. No new
watchdog mechanism is approved by this finding.

### F6 — The security work plan uses the wrong generation width and lacks a safe reuse rule

**Definite field-width conflict, plus missing lifecycle policy.**

- `docs/golden-tokens.md:122–129` and `docs/GoldenDetails.md:69, 271–275`
  specify 9-bit generation fields, with 512 possible values.
- `docs/phase-1-security-todo.md:288–310` directs implementation of **7 bits**,
  modulo **128**, and a one-second wrap-frequency guard.
- `docs/namespace-security.md:10–15` also retains the older 7-bit entry layout.

Changing 128 to 512 fixes the width but not the lifetime argument: after a full
cycle, an old GT can have the same slot and generation as a new occupant.
A minimum time between wraps does not establish that old GTs are gone.

**Required resolution:** align the work plan with the selected layout, and
define the Phase 1 rule preventing stale authority from reviving on reuse
(including exhaustion/wrap handling). Specify the rule and its evidence before
claiming safe revocation. The work plan also calls itself “Non-Silicon Tasks”
while this item requires a hardware guard; clarify that scope.

### F7 — integrity32 does not have one consistently stated input mask

and a board-resource inventory.

Those goals are not inherently incompatible, but the collection does not bind
them to one approved **required / deferred / unsupported** release matrix.
`docs/releases/isa-to-fpga-alignment-plan.md:126–142` explicitly requires such a
decision ledger. Identify the exact edition and approval of each controlling
contract, required services, allowed resident set and acceptance target.

### M2 — Complete approved instruction encodings and reset binding

The master already lists the missing direct CHANGE allocation, separate indexed
CALL transcription, reported INDEX deferral record, reset fetch/grant/entry/slot
contract and proposed fault allocations. The petname document additionally
leaves CALL/LAMBDA bit allocation pending. Required deliverables are exact legal
and illegal vectors, condition/fault precedence, state effects and word-by-word
disposition for the legacy and withdrawn candidates—not just round trips.

### M3 — Mint's bounded mechanism and callable ABI

`docs/ide-mint-forge-contract.md:57–89, 125–164, 202–214` and the supplied
bounded-rule note still require proof issuance/verification, operation
authorization, ABI locations, create-only versus replacement selection, writer
exclusion/accepted writes, reset/fault completion bounds and publication timing.

Cooperative execution excludes scheduled software interleaving only. It does not
by itself prove external-writer exclusion or reset-safe completed writes.
Conversely, a full transaction engine is **not** automatically a Phase 1
requirement: the supplied R1–R3 bounded rule is the intended narrower scope.
No verifier/register numbers or hardware timing values should be invented.

### M4 — End-to-end System lifecycle acceptance

`docs/system-namespace-handoff-contract.md:163–180` explicitly leaves delivery,
diagnostic invalidation, lazy-load ownership/resume, tunnel lost replies,
peer restart/partition behavior, GC roots/reuse and board-resource authority
unresolved. Decide which are Phase 1 requirements and specify those selected.
Record the remainder as deferred; do not silently expand Phase 1 to solve all
networking or distributed-commit questions.

### M5 — Candidate-bound evidence and observational coverage

The master records cutover checks as NOT RUN; the release plan requires identical
frozen inputs and architectural checkpoints across simulator, RTL and FPGA.
`reports/bitstream-candidate-readiness.md` records a not-ready candidate with
open gates. Prepared-Thread replay is explicitly isolated simulator evidence.
The Wukong runbook describes a dated physical verification procedure; it is not
proof that a newly selected ISA/image passed it.

Missing from this collection is a complete approved candidate evidence package:
exact revisions and hashes, layout/checkpoint vectors, per-consumer results,
physical observations and justified exclusions. This is **absence within the
reviewed collection**, not a claim that no other project evidence exists.

## Differences deliberately not classified as new defects

- Earlier IRQRETURN candidates and split-magnitude encodings are frozen,
  explicitly unapproved proposals. Their difference from the master is expected.
- mLoad and trusted-security-base legacy CRC/permission descriptions have
  explicit historical/non-authoritative warnings.
- Historical ISA reference/encoding and baseline reconstruction are evidence,
  not independent current ISA definitions.
- Experimental IDX1 has an explicit separate-profile boundary. Its 20-bit
  magnitude is not a selected LOAD/SAVE layout conflict by itself.
- Prepared-Thread replay explicitly retracts its earlier implicit-CALL result.
  Keeping that correction history is appropriate.
- The parity/ECC note separates bit-error protection from authenticity; neither
  should be relabeled as a cryptographic guarantee.
- Compact API unsupported/private forms and LUMP future-normative enforcement
  notes are declared boundaries. They need release applicability, not a blanket
  assertion that every planned feature is missing from Phase 1.
