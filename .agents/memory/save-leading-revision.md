---
name: Save advances the IDE
description: Successful LUMP saves are explicit authority to advance the matching IDE working selection, not merely publish to a detached library.
---
Saving a new LUMP must realign the IDE to that exact saved revision: repository,
History, matching Namespace selection, and validated private simulation.

**Why:** The user explicitly rejected a successful save leaving History and
execution on obsolete artifacts: “the leading edge of progress instead of a
stale, outof date solution”. This supersedes the earlier artifact-only-save UI
policy for the IDE working selection.

**How to apply:** Preserve immutable history and unrelated assignments. Stop
stale execution before replacing a whole validated simulation; never splice
live code and c-lists or touch hardware. Failed downstream preparation must
not roll back a successful artifact save or masquerade as current execution.
New unassigned copies need an explicit destination; unsupported design-profile
admission must remain blocked rather than borrowing a legacy image.

Every successful save must refresh History independently of editor reload,
Namespace alignment, and simulation admission.

**Why:** The user reiterated this after seeing the old CapabilityTest History
despite a newer save. Correcting a History cache flag alone was insufficient
while earlier post-commit failures could still skip the refresh.

**How to apply:** Treat History as a commit acknowledgement, not a downstream
simulation success effect. Verify failure paths as well as successful alignment;
keep the exact displayed artifact authoritative for its tabs.

The successful-save contract applies to all entry points, including automatic
compile saves and reconciled commits, not just the main Save dialog.

**Why:** A repeated stale-History report in the workspace preview exposed that
the dialog-only correction left automatic saves unhandled. Browser inspection
confirmed exact-record History refresh worked, but those saves never called it.

**How to apply:** Enforce History acknowledgement at the shared commit boundary.
Distinguish an old Namespace assignment from a stale History fetch; do not
silently merge separate abstraction identities or substitute their binaries.

When the user asks to recover a saved LUMP, correct the existing stale working
selection as well as future save behavior, using the ordinary protected-change
review and exact artifact hash.

**Why:** Fixing future refresh hooks did not repair the already-stale Namespace
assignment; repeated screenshots still showed the old artifact after reload.

**How to apply:** Verify the saved binary first, preserve other rows and history,
then persist only the authorized matching design selection. Verify a full reload,
not merely a temporary library selection. Do not activate simulation or hardware
as a side effect of this recovery.

Saved-artifact inspection must separate saved LUMP revision, identity issue,
authored source version comments, and runtime/session evidence.

**Why:** The user requested removing duplicate and misleading fields and
deriving the inspected information from the selected saved revision.

**How to apply:** Use the exact token/filename/hash and saved revision; label
publication timestamps as saved times, not compilation times. Do not rewrite
immutable binaries or authored comments just to make different version concepts
look equal. Keep runtime counters outside saved-artifact evidence.

For ascending designs, private replay and the historical IDE machine must stay
separate until ordinary IDE controls explicitly support both runtime models.
Do not make a successful save clear the historical execution barrier merely
because a separate ascending replay was admitted.

**Why:** The ascending core intentionally excludes legacy host dispatch and
slot metadata. Treating it as an interchangeable historical machine would
silently restore authority that the selected profile does not have.

**How to apply:** Keep fresh replay visibly identified as the selected design's
private simulation. Candidate review alone remains insufficient authority.

The user requires all simulator execution to follow the selected view and
rejects SelfTest as an implicit fallback. Main controls must dispatch to the
selected design's admitted runtime or stop; they must not run the historical
image behind a newer saved-artifact view.

**Why:** A selected v2 design and a legacy simulator image coexisted, allowing
ordinary Run to execute old code despite the corrected repository selection.

**How to apply:** Validate the selected saved identity and Namespace ownership
before execution and across asynchronous work. Remove auto-inserted SelfTest
defaults, preserve historical files and deliberate user assignments, and never
substitute an old image when admission or a dependency fails.

Do not reintroduce the “Released to build handoff” checkbox or a release-status
dependency for inspecting or using saved LUMPs.

**Why:** The user explicitly identified this setting as stale and asked to remove
both the control and code watching it.

**How to apply:** Saved revision/date/History metadata is read-only and independent
of old handoff records. This does not remove binary validation or explicit
Namespace/configuration approval.

Do not display a persistent successful-save popup: saved identity already has
an editor presentation. Pending and failed saved-revision status notices must
remain dismissible. Dismissing a
notice hides presentation only; it must not clear execution barriers or cancel
preparation. Closing must stay effective for that notice across rendering and
page reloads, rather than redisplaying the same acknowledged status.

**Why:** The user identified the persistent success notice as uncloseable after
its wording was corrected, then explicitly objected when it repeatedly
returned after closing. The user supplied a screenshot of the same green
success popup returning despite the separate dismissal marker. Success must
stay absent even when that marker is missing. A notice is not itself execution authority.

**How to apply:** Keep the Close action separate from status-clearing or
activation functions, including for pending and failed preparations. Preserve
dismissal separately from the underlying execution state.

Selected-design execution must retain the established numbered Boot and Code
step output and trace displays, including Step, Walk, and Run. The Simulator
Trace window itself must show the three Boot instructions as well as Code;
restoring Console Output or the separate pipeline view is not sufficient.

**Why:** The user reported the loss of the familiar execution steps after the
selected-design execution path was introduced. Runtime selection must not
silently remove existing debugging feedback. The user explicitly corrected
verification that treated console steps as proof the Simulator Trace window
was restored.

**How to apply:** Reuse the existing trace presentation and preserve captured
instruction evidence when appending later console output.

Every selected simulator must present the existing fault modal on a runtime
fault, not merely write console output or show a toast.

**Why:** The user observed the selected simulation stop on CHANGE without the
normal fault report. Changing runtime ownership must retain fault presentation.

**How to apply:** Keep fault recall, exact incident evidence, notification
failure containment, and modal presentation consistent across execution paths.
