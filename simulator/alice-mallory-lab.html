Tuple containment evidence

The tuple tests use the existing 58-word Thread heap record, not the designer’s illustrative 18-word layout. Alice and Mallory run in separate Threads. Alice uses her CR5 heap; Mallory’s test driver has no grant to Alice’s heap. The allocator reserves fixture storage; real DWRITE/DREAD instructions exercise Alice’s access. Mallory’s baseline DREAD through empty CR4 faults NULL_CAP. With valid own CR5, indexed DREAD/DWRITE attempts targeting Alice’s tuple and immediate attempts one word past Mallory’s authorized Thread range fault RANGE without retiring. The existing instruction gate checks the owning Thread’s Namespace range, not a tuple ACL or the narrower heap layout. A positive DREAD at the same tuple-relative offset reads Mallory’s own record, not Alice’s. Denied attempts check exact first-fault evidence, unchanged data registers, and every Alice tuple word. No tuple ACL or new security mechanism is introduced. The tuple regression uses explicitly pinned baseline Alice/Mallory fixtures, not the latest editor revisions. This is a bounded simulator regression, not a proof for every attack, FPGA validation, or a Dijkstra messaging test.
