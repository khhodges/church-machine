M-bit control abstraction — interface proposal

Review only. This defines a proposed software abstraction over the existing protected hardware-control word. It does not add ISA opcodes, change the master ISA or authorize implementation, synthesis or board actions. MBit is a working interface name, not an allocated canonical artifact identity.

Purpose and authority

Expose bounded functions rather than a raw register setter. Bits 0–15 control CR0.M–CR15.M; bits 16–31 are for hardware controls, including watchdog refresh. The exact watchdog bit and command semantics still require approval.

The abstraction must not return or export the writable control-object GT. An executable GT authorizes entry, but that alone must not imply permission to invoke every privileged operation with arbitrary operands. Each method needs an explicitly authorized caller and a defined, limited effect.

Existing custody is Namespace-only. The proposed interface can be supplied by Namespace or delegate a complete operation to it before any M bit is armed. Moving custody to a new standalone abstraction would be a separate reviewed change; merely naming MBit does not grant it hardware access.

Initial method contracts

Proposed method Authorized caller / GT sources Effect Must not do
RefreshWatchdog() Approved scheduling authority; provider's protected control-object GT authorizes the write Restart the fixed one-second deadline through the proposed refresh command, before expiry Change the duration, clear an existing fault, grant M authority, toggle the fault LED or let an ordinary worker repeatedly feed the watchdog
SaveCR12(destinationCList, index) Caller explicitly authorized to export the current Thread GT; provider's control-object GT authorizes arming CR12.M; destination GT independently supplies Church S authority Check the request, arm CR12.M, perform the specific SAVE from CR12 into the authorized destination, and finish without leaving CR12.M armed Return after merely setting M, export to an unchecked destination, access a different Thread, or run caller-supplied code while M is armed

SaveCR12 is an initial example of set CR12.M + operation, not approval of every operation on CR12. Additional operations should receive distinct method contracts with named operands, authority checks and postconditions. No generic SetM(register, value), raw WriteControlWord(value) or privileged callback executor is proposed for callers.

Functional requirements

  • The instruction and authorizing GT remain independent. Every applicable access passes mLoad and the operation's other security checks. M contributes only the authority explicitly defined for that register and operation.
  • Caller authorization precedes arming M or refreshing the timer. Delegation must not turn an unauthorized request into an authorized one merely because a trusted helper forwards it.
  • The M-authorized operation belongs inside the method. No caller callback, yield or intervening CALL/RETURN may carry an armed M bit to unrelated code. Current CALL/RETURN M rules must be reconciled with the method's ABI; this is not equivalent to calling a setter and then executing an operation afterward.
  • Successful SAVE consumes CR12.M under its defined ISA rule. Normal method return must not leave CR12.M armed or newly elevate unrelated registers.
  • On a fault, do not claim software cleanup executed. Preserve the ISA-defined fault evidence; recovery must not expose armed M authority to untrusted execution. The exact fault/recovery M-state contract remains an adoption requirement, not a new implicit ISA exception.
  • A control-word write must deliberately account for the low sixteen bits. Under existing full-word semantics, writing only the refresh bit would clear them. Do not replay other upper command bits or assume a stale whole-word value is safe. Exact preservation and readback semantics need definition.
  • Watchdog expiry, not refresh, toggles the LED. Repeated one-second expiries give the requested one-second-on / one-second-off cycle, subject to recovery timing. The indicator is not a free-running heartbeat.

Decisions required before implementation

  1. Exact method-entry authorization and delegation rules. A shared callable interface must not let refresh-only callers invoke M-authorized operations.
  2. Refresh command bit, readback, unrelated-bit handling and expiry precedence. Suggested command behavior is write-one refresh, no persistent hold-off.
  3. Method operands/results and their CALL/RETURN register contract.
  4. The complete list of allowed M-authorized operations and fault postconditions.
  5. Reconciliation with the earlier automatic-handoff renewal proposal: explicit protected refresh must not coexist with an unintended second renewal path.

The watchdog duration remains fixed at the proposed one second; setting a new duration is not part of this interface. The existing red-text ISA review predates this interface and the save-first recovery discussion and still requires reconciliation before adoption.
