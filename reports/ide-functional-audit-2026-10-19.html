Priority findings

F01 · High · Confirmed execution failure; cause not yet established

The selected CapabilityTest stops at CHANGE after boot

Browser and direct-engine runs on the same saved image halt at NIA 0x000F / physical 0x0710 with “CHANGE requires a non-null Inform Thread GT”. Boot restoration did not remove this later fault. Evidence predates this audit sweep and refers to the unchanged selected image.

Evidence location: simulator/simulator.js: _activateChangeThread; selected Namespace bindings

Recommended correction: Trace the exact instruction operand, saved bytes, localized C-list and target descriptor. Do not weaken fault gates, assume user error, replace v2, or restore intentionally removed Mint.

F02 · High · Confirmed control-path omission

Breakpoint settings are not honored by selected-design Run/Walk

app-run.js returns early into DesignSimulation.command for the active selected-design profile. That loop never invokes checkBreakpointBeforeExecute or the boot-LOAD breakpoint helper. The legacy loop does.

Evidence location: simulator/app-run.js: stepSim/runSim/walkToggle; simulator/design-simulation.js: execute/run

Recommended correction: Use shared execution gating with explicit profile semantics. Test boot and program pause/resume, one-shot behavior and Reset.

F03 · High · Confirmed isolated control-loop reproduction

Run keeps stepping while waiting for a LUMP

An isolated existing control harness returned {suspended:true}, set awaitingLump, and counted 250 step calls in the first Run batch; running remained true. The selected loop checks halted but not awaitingLump/_lazySuspended. The legacy simulator run checks these states. This demonstrates the controller defect, not a live missing-LUMP incident.

Evidence location: simulator/design-simulation.js: execute/run; simulator/simulator.js: run/_stepExecution

Recommended correction: Stop batching on suspension and expose a truthful waiting state. Resume only when the owning load completes and selection still matches.

F04 · High · Confirmed source inconsistency; UI reachability is profile-dependent

Boot inspection still uses legacy slots and obsolete GT constants

_renderBootNSDecoder reads NS[0] as root and NS[1] as Thread, labels Thread as NS[1], and displays 0x00800000/0x00800001 as hardware GTs. Current GT parsing treats these as NULL; selected ascending execution uses metadata slot0, root1, Thread2. The inspector can contradict real boot.

Evidence location: simulator/app-absdetail.js:140–235

Recommended correction: Drive inspection from the selected profile and actual descriptor/boot evidence. Never present historical constants as current observed hardware.

F05 · Medium · Confirmed version mismatch; stale-cache incident not reproduced here

Eleven loaded scripts have outdated hash version tags

Full served-script inventory found 11 SHA tag/content mismatches, including compiler, API contract, save handling and shell code. A live compiler response used Cache-Control: no-cache, must-revalidate, which mitigates normal browser staleness. A mismatched tag alone does not prove stale execution.

Evidence location: simulator/index.html and script inventory below

Recommended correction: Generate/check all cache keys together, not only the five execution assets currently covered by the focused test.

F06 · Medium · Confirmed duplicate definitions and differing semantics

Four global HTML escaping helpers overwrite one another

_escHtml is declared in app-shell, app-compile, app-run and app-misc. Later script order wins. Implementations differ for zero/null and apostrophes. No exploit is claimed. The separate regex hit for _openBootExecutionUpdate includes source strings, not three real global declarations.

Evidence location: simulator/app-shell.js:1061; app-compile.js:211; app-run.js:15334; app-misc.js:2184

Recommended correction: Consolidate one helper with a documented text/attribute contract and tests. Do not perform a broad replacement without checking contexts.

F07 · Medium · Confirmed test health issue; not 81 confirmed product bugs

The existing test inventory cannot currently establish a clean release

289 standalone test programs were run in private copies: 208 exited successfully, 81 failed or timed out. Failures include missing fixtures, dependency/global setup, old boot labels, canonical identity requirements and unresolved execution expectations. Individual assertion counts are not claimed.

Evidence location: Per-program appendix below

Recommended correction: Reconcile each failure against current requirements; repair fixtures only when the contract is proven correct. Keep unresolved runtime failures distinct from obsolete tests.

F08 · Medium · Confirmed documentation mismatch

Project entry-point and hardware descriptions disagree

replit.md describes the simplified S-IDE entry-point with debug-only advanced views; the main simulator manifest contains 22 views. package.json describes Tang Nano as target, while project maintenance policy identifies Wukong A7 as current. Multiple products/profiles need explicit scope rather than contradictory global descriptions.

Evidence location: replit.md overview; package.json description; simulator/index.html

Recommended correction: Document which entry-point and profile is current, supported or historical. Do not delete legacy functionality based on copy alone.

F09 · Medium · Confirmed control-path inconsistency

Continuous-run settings are bypassed by selected-design execution

Legacy controls consult continuousRun. The selected-design run loop does not consult that setting and batches 250 instructions until stopped/halted. Exact user-visible end-of-run behavior needs a targeted acceptance test.

Evidence location: simulator/app-run.js: continuousRun and runSim; simulator/design-simulation.js: run

Recommended correction: Define consistent settings behavior across profiles and test each supported stop condition.

### Confirmed defects / inconsistencies
1. **Programs / Editor navigation misroutes.** Selecting the normal menu destination opened an unrelated read-only “Unnamed — executed code” dialog and remained on Dashboard instead of opening Editor. Editor was reached only with the explicitly labeled fallback. Screenshot `ry7t7c`.
2. **Source Library navigation misroutes.** Code → Source Library opened a blank Create Abstraction wizard at `/start/~/r20260527z?abstraction=1`, not the Source Library. The actual Source Library subtab under Abstractions loaded correctly. Screenshot `8lc7w2`.
3. **Pipeline boot operands disagree with the ascending Namespace layout.** The displayed rows are `LOAD CR15, CR15[0]`, `CHANGE CR12, CR15[1]`, `CALL CR0`; the ascending layout has the boot entries at slots 1 and 2. Screenshot `e05ztq`.
4. **Pipeline 7-Step mode clips horizontally.** The RETURN row is partly outside the desktop viewport. Screenshot `m7how0`.
5. **Testing monitor reports contradictory board state.** After an additional poll it still said “No trace packets ever received” and “no trace yet,” while `CURRENT EXECUTION` said “Why execution stopped: recent board trace activity.” No board controls were used. Screenshot `0hoqbx`.
6. **Source Library instruction/control mismatch.** The page says “Click Source on any card to expand,” but visible cards expose only “Load → Editor”; clicking the Contact card label did not expand a source preview. I did not use Load → Editor because that changes the editor buffer, so actual source text remains unverified. Screenshot `d319jm`.
7. **Device onboarding/status mismatch.** A “First boot! Your Ti60-Full is online” callout appeared beside a Ti60-Full card marked Offline · 107d ago. Treat the callout as stale until its intended historical meaning is clarified. Screenshot `x7cigs`.

### Suspected/stale data, not confirmed defects
- LUMP History showed the current v2 and two v1 rows with the same timestamp; one v1 row was ineligible for current selection. Possible duplicate lineage/history entry. Screenshot `wa1pkd`.
- Builder Versions showed four repeated `version unknown` history entries with the same placeholder-looking hash `0123456789ab`; treat as suspect history data. IDE/GitHub also reported 76 differing files, FPGA/USB-UART offline, firmware v20, and a pending next release. Screenshot `eudh2y`.
- Devices Reliability showed one row `Slot ? / system / — / 3,223 faults / 1.2h MTBF`; the missing slot identity is suspicious but may represent an intentional aggregate. Screenshot `yntlws`.
- The DOM contains duplicate `id="absSearchInput"` values across visible/hidden views. The ID selector was ambiguous; selecting the accessible visible textbox by its label worked.
- Source Library initially warned that `window._cloomcExampleSources` was not set; the scaffold list populated after about 1.2 seconds. No persistent loading state was observed.

### Console/network observations
- Initial page load had no recorded resource failures; no uncaught page error was captured in the Versions check.
- Six HTTP 401 responses were recorded while loading protected Builder approval/version data, including `/api/build-approval/ns-map`, `/api/wukong-build/status`, `/api/artifact-revisions/namespace`, `/api/artifact-revisions/bitstream`, and `/api/build-approval/snapshot/latest` (one endpoint repeated). The UI says protected approval data requires `REPORT_TOKEN`; none was supplied, so these are recorded as expected gating, not treated as an application defect. One additional 401 appeared on Builder Testing; its URL was not retained in the available output.
- Some device event/status requests were aborted during navigation; no evidence established these as application failures.
